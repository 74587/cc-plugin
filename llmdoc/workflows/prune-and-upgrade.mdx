# Prune 与 Upgrade

## Prune 收敛知识价值

CLI 的 `prune --report` 只提供规模、重复和碎片等机械信号；没有候选不代表正文知识密度合格。`recorder` 还必须逐段应用 Stable Knowledge Gate，删除可从源码、schema、help、测试或 CI 快速重建的库存，同时保留决策理由、边界、不变量、契约、失败语义和危险工作流。

报告同时列出 startup preload 持久引用，使人工 merge/delete 在动作前看见配置影响面。直接 rename 交给 `mv` 事务性同步；人工合并或删除必须在同一写集中更新或移除受影响的 `llmdoc.config.json` 条目。缺失目标会被 validate 判错并阻止 commit，这是防止悬空启动承诺的故意门控，不应通过跳过配置校验绕开。

收敛不能靠 archive、搬运低价值内容、无脑按时间删除或把无关路径挂到文档维持 coverage。success 要求知识密度或路由实质改善、validate 通过，并且合理的 `code.paths` 仍准确。

当前 convergence 快照没有 prune 后的独立刷新入口，因此规模下降后 growth gate 可能继续显示 above；在 CLI 提供受控刷新能力前，以本次 report 的实际规模和候选为准。该限制消失时应删除这条过渡说明。

## Upgrade 始终显式

upgrade 不属于 update、prune 或 hook 的隐式路径，也永不主动建议。CLI 只盘点 legacy/V2 结构并给出诊断；`recorder` 负责语义迁移，不自动搬运或删除正文。

若迁移后没有 ledger，必须先 `init-state`，再 validate，最后用 `commit --all` 收尾；顺序错误会让校验缺少有效性台账。工作流契约与 CLI 当前能力不等价时，稳定文档必须明确人工判断边界，不能把诊断命令描述成自动完成迁移。

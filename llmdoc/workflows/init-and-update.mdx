# Init 与 Update

## 共通前置条件

两条命令都要求在第一次正式写入前先满足 `git status -- llmdoc/` clean。写完后必须跑 `validate`；如果校验失败且当次无法修复，命令文档要求回滚写入后再汇报失败。

## init 什么时候该跑

`init` 只用于“仓库还没有有效 V3 `llmdoc/`”的情况。当前命令契约明确拒绝两类情况：

- 已经存在有效 V3：应转去 `update`
- 发现 legacy 布局：应转去 `upgrade`

成功的 init 需要完成三件事：调查仓库表面、由 `recorder` 写出第一版 V3 知识面、再用 `validate` 收口。

## update 如何选择 light 或 deep

`update` 的入口是 `status`、`delta`，以及显式声明的 reflection candidates：

- light：受影响文档或候选 owner 已映射、事实边界清楚，直接让 `recorder` 从 CLI 证据同步文档
- deep：出现 unmapped files、候选 owner 或根因不清、结构边界变化、事实冲突、影响过广，或有文档缺少/失去有效 `validatedRevision`，先由 `investigator` 产出 scoped 报告，再交给 `recorder`

命令文档把源码编辑排除在授权之外；update 只同步 `llmdoc/` 与 `meta.json`。

## reflection candidate 的晋升门

`/llmdoc:update --reflection` 才授权工作流读取并处理声明的候选；省略路径时读取 `.llmdoc-tmp/reflections/pending/` 直属的 Markdown 候选。pending candidate 本身就是 update 信号，即使没有代码 delta 也要进入复核。

候选必须包含可核对的 trigger、错误假设或动作、根因、预防规则、作用域与置信度。用户纠正可以确认意图，但仓库事实仍要由代码、测试或稳定文档验证；通过 `search` 和定向 `show` 找到 owner 并查重后，`recorder` 只把可复用的成熟规则折入既有 architecture/guide，不创建 tracked reflection 文档。晋升、已覆盖或驳回的候选由 calling workflow 归档到 resolved；流程 incomplete/failed 时保持 pending。

## recorder 与工作流的收尾分工

写入之后的收尾按角色分两段：

- `recorder` 只负责跑 `validate` 并修复它报告的全部失败，然后汇报写集；它不执行最终收尾，也不手工拼出 `commit` 的等价序列。只有当工作流明确要求“只刷新 revision、不提交”时，recorder 才自己跑 `fingerprint --update`。
- 最终收尾归 calling workflow：用 `npx -y @tokenroll/llmdoc commit -m "<message>"` 一次完成（`--all` 做全仓验证并推进 baseline；内部序列见 `cli-runtime/retrieval-and-mutation.mdx`）。

## 合并方式对 revision 的影响

`commit` 烙进 `meta.json` 的 baseline / `validatedRevision` 锚定的是当时分支上的真实 commit hash。任何重写 hash 的操作都会作废刚烙的 revision——除了已知的“不要用 `--amend` 并 meta commit”，rebase merge 与 squash merge 同样会重写 hash，使 `meta.json` 里的 revision 脱离 main 历史。这种破坏是隐性的：本地仓库里旧 commit 对象仍可解析、validate 照常通过，但 CI fresh clone 中该 revision 不可达、validate 必失败。因此带 fingerprint / meta 变更的 PR 必须用 merge commit 合并（保留原 commit），或直接在目标分支上收尾；已经踩中时，在合并后的历史上重跑 `fingerprint --all` 并提交即可修复。

## dirty worktree 的完成语义

当稳定文档已反映工作树实现、但相关源码尚未提交时，`baseline.revision` 与各文档 `validatedRevision` 仍必须锚定真实 HEAD，不能伪造“工作树 revision”。`status` / `delta` 会诚实地把这些文档标成 dirty 或 impacted；update 可以完成文档同步，但不能把这类状态包装成“已提交且已 fingerprint 的 clean revision”；真正清除 dirty/impacted 信号，要等用户提交相关实现后再运行 fingerprint（或 `llmdoc commit --all`）。

## 结束条件

update 成功前至少要有：受影响文档已改写完、recorder 的 `validate` 全部通过、工作流已用 `commit` 收尾。结果状态固定只有五个：`success`、`no_change`、`dry_run`、`incomplete`、`failed`，不要在 stable docs 里发明第六种“半成功”。最终汇报以 `validate` 与 `commit` 的结果为准，不再单独汇报一次独立的 fingerprint 步骤。
